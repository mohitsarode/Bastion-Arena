1. PLAIN-ENGLISH SYSTEM ARCHITECTURE (FOR AI & NON-AI FACULTY)

To understand the insider attack simulations, this section explains how Bastion Arena operates using fundamental backend engineering concepts (REST APIs, SQLite databases, and background tasks) without unnecessary jargon.

What is Bastion Arena?

Imagine a competitive coding platform (like LeetCode) or a CI/CD test pipeline, but designed for Artificial Intelligence Models (LLMs). Red Team testers submit complex adversarial prompts to test if the AI model breaks, while Blue Team filters try to intercept malicious prompts.

Why is an Insider Attack Dangerous Here?

If a malicious employee, rogue evaluator, or database admin can silently change test results or delete log entries, a dangerous AI model could be certified as "safe" and deployed into hospitals, banks, or critical infrastructure.

The 5 Core Components in the System:

Component Actor Role Responsibility in the Evaluation Pipeline
Red Agent Untrusted Tester Submits prompts (both normal questions and jailbreak attacks) to test the model's safety limits.
Blue Defense Safety Gatekeeper Scans incoming prompts for attack signatures (e.g. "ignore previous instructions") and scrubs sensitive credentials.
Model Under Test (MUT) AI Engine The target language model generating responses to user prompts.
Neutral Evaluator Independent Judge Inspects the prompt and the AI output, grading whether the model safely refused or got bypassed (0 to 2 scale).
Arbiter Control Plane Central Security Broker Enforces token authentication, manages quotas, masks internal defense details from the user, and signs every event to the audit database.

Three Critical Backend Mechanisms Explained Simply:

1. Zero-Trust Information Hiding (Why we mask defense details):
When a hacker tests an AI, if the API returns: "Error: Blocked by regex rule 'ignore_instructions_v2'", the attacker now knows exactly which filter caught them and will easily rewrite their prompt to bypass it. Bastion Arena's fix: The Arbiter intercepts all responses and only returns generic high-level numbers (refusal: 2, bypass: 0). The attacker never sees internal defense rule names or evaluator reasoning.
2. Shadow Execution & 500ms Latency Bucketing (Neutralizing Timing Attacks):
If an input filter blocks a prompt, it normally rejects it in 5 milliseconds. But if a prompt passes and queries the AI model, it takes 500 milliseconds. An attacker can use a stopwatch to detect if they bypassed the input filter! Bastion Arena's fix: When Blue blocks an attack, Arbiter silently runs a background Shadow Execution of the model and delays the response to a fixed 500ms time bucket. Every request takes 500ms, completely blinding the attacker.
3. Cryptographic Append-Only Ledger (ADR-005 Tamper Engine):
In a regular database, an insider with SQL access can run: UPDATE events SET status = 'ALLOW'; without detection. In Bastion Arena, every event is chained to the previous event using a SHA-256 hash and digitally signed with Ed25519. If a single character in the database is modified, the hash chain breaks immediately.

5. DETECTION, MITIGATION & COUNTERMEASURES (RUBRIC ROW 4 — 4 MARKS)

A. Layered Security Model (IITK NPTEL Cyber Security Framework)

1. Zero-Trust Architecture

Every participant (Red, Blue, Model, Evaluator) runs in an untrusted sandbox. All communication must pass through the Arbiter control plane with strict capability tokens.

2. Principle of Least Privilege

Workers execute as unprivileged non-root users (UID 10001) with all Linux capabilities dropped (cap_drop: [ALL]) and read-only filesystems.

3. Data Loss Prevention (DLP)

Blue Agent's OutputRedactor performs real-time regex token scrubbing on all outgoing streams to intercept canary secrets and API keys.

4. Honeypot & Deception Defense

Arbiter's Shadow Execution engine runs dummy model invocations when an attack is blocked to deceive the adversary and eliminate timing side-channels.

C. Viva Defense Preparation Guide (Top 5 Questions & Model Answers)

Q1: What is the main difference between a traditional database audit log and Bastion Arena's ledger?

A: A traditional database stores raw rows. An insider with SQL access can edit or delete rows without leaving a trace. Bastion Arena links every row using SHA-256 hashes (like a blockchain) and signs them with Ed25519. In ADR-005, the verifier recomputes the hash from the raw data fields — if a single character is modified, the check fails immediately.

Q2: How does your system prevent an insider from exploiting "Timing Side-Channels"?

A: Normally, blocked prompts return in 5ms while passed prompts take 500ms. An attacker measures response times to learn if their prompt reached the AI. Bastion Arena implements "Shadow Execution" — when an attack is blocked, we still run the model in the background and quantize the total response time to a fixed 500ms bucket, blinding the attacker.

Q3: How does Bastion Arena enforce the Principle of Least Privilege?

A: At the container layer, all processes run as non-root (UID 10001) with all Linux capabilities dropped (`cap_drop: [ALL]`). At the API layer, requests require fine-grained capability tokens; a Red tester token cannot access internal Blue inspection or Auditor forensic endpoints.

Q4: Why does Bastion Arena mask internal defense rules from Red Team users?

A: Under Zero-Trust Information Hiding, if an API tells an attacker "Blocked by regex rule XYZ", the attacker can incrementally mutate their prompt until it bypasses the rule. By returning only normalized categorical scores, the attacker cannot reverse-engineer our defensive signatures.

Q5: What standard compliance models did you map your mitigations to?

A: We mapped our layered defenses to the IITK NPTEL Cyber Security framework (Zero Trust, DLP, Least Privilege, UAM, Honeypots) and international standard ISO/IEC 27001:2022 (Controls A.5.15, A.8.15, A.8.17, and A.8.24).
